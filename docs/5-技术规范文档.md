| `pkg/` | 可复用的公共库，可被其他项目引用 | 外部可引用 |

## 三、代码规范

### 3.1 命名规范

| 类型 | 规则 | 示例 |
|------|------|------|
| 包名 | 小写、单数、无下划线 | `handler`, `service`, `model` |
| 结构体 | 大驼峰（导出） | `ClientManager`, `MessageRouter` |
| 接口 | 大驼峰，单方法可加 `-er` | `MessageSender`, `ConnectionManager` |
| 函数/方法 | 大驼峰（导出）或小驼峰（私有） | `BroadcastToAll`, `sendToClient` |
| 变量 | 大驼峰（导出）或小驼峰（私有） | `clientID`, `lastPong`, `SendChan` |
| 常量 | 大驼峰或全大写 | `DefaultPingInterval`, `MAX_BUFFER_SIZE` |
| 文件名 | 小写，下划线分隔 | `client_manager.go`, `ws_handler_test.go` |
| 缩写词 | 导出时全大写（URL、HTTP、API、IP、ID）；私有时全小写 | `LongURL`, `HTTPClient`, `UserID`；`url`, `httpClient`, `id` |

### 3.2 注释规范

- **包注释**：每个包必须有一个包级注释，写在 `package` 声明上方，说明该包的职责。
- **导出符号注释**：所有导出的类型、函数、常量必须有文档注释，以符号名开头。
- **复杂逻辑注释**：对于复杂的业务逻辑（如非阻塞发送策略、优雅退出流程），须添加行内注释说明设计意图。

**示例**：

```go
// ClientManager 管理所有在线 WebSocket 客户端。
// 内部使用 sync.Map 保证并发安全，支持注册、注销和按 ID 查找。
type ClientManager struct {
    clients sync.Map
}
```

### 3.3 错误处理规范

- 使用 `fmt.Errorf` 或 `errors.New` 创建错误。
- 在 `service` 层向上返回明确的错误类型（如 `ErrClientNotFound`、`ErrRoomNotFound`）。
- 在 `handler` 层根据错误类型设置对应的 HTTP 状态码（404、500 等）。
- 禁止忽略错误（`_` 接收），必须显式处理或向上传递。

### 3.4 代码风格

- 使用 `go fmt` 自动格式化所有代码。
- 使用 `go vet` 检查潜在的代码问题。
- 使用 `go mod tidy` 保持 `go.mod` 和 `go.sum` 的整洁。
- 每行长度建议不超过 120 字符。
- 导出函数按逻辑分组，使用空行分隔。
- 禁止在业务代码中使用 `panic`（仅在初始化失败时使用）。
- 所有 `goroutine` 的启动必须明确其退出条件（通过 `context` 或显式关闭信号）。

## 四、配置规范

### 4.1 配置文件格式

使用 TOML 格式，示例 `configs/config.toml`：

```toml
# WebSocket 网关配置文件

[server]
port = 8080
read_timeout_seconds = 60
write_timeout_seconds = 60

[websocket]
ping_interval_seconds = 30
pong_wait_seconds = 60
write_wait_seconds = 10
max_message_size_bytes = 5120
send_buffer_size = 256

[graceful_shutdown]
timeout_seconds = 5

[log]
level = "info"                      # debug, info, warn, error
format = "json"                     # json, text

[metrics]
enabled = true

[redis]                             # 可选，多实例消息广播
enable = false
url = ""
channel = "ws:gateway:message"
```

### 4.2 配置加载流程

1. 默认加载 `configs/config.toml`。
2. 支持通过环境变量覆盖关键参数（如 `WS_PING_INTERVAL`、`WS_PORT`）。
3. 加载完成后执行校验（如端口范围、超时值正数等），校验失败则启动失败。

### 4.3 环境变量覆盖规则

环境变量以 `WS_` 为前缀，如：

| 配置项 | 环境变量 | 默认值 |
|--------|----------|--------|
| 端口 | `WS_PORT` | 8080 |
| Ping 间隔 | `WS_PING_INTERVAL` | 30 |
| Pong 超时 | `WS_PONG_WAIT` | 60 |
| Send 缓冲区 | `WS_SEND_BUFFER` | 256 |
| Redis URL | `WS_REDIS_URL` | "" |

## 五、日志规范

- **日志库**：使用 Go 标准库 `log/slog`。
- **输出格式**：生产环境使用 JSON 格式，开发环境可切换为 text 格式便于阅读。
- **日志级别**：支持 `debug`、`info`、`warn`、`error` 四个级别，通过配置文件控制。
- **结构化字段**：关键事件必须包含结构化字段，如：

| 事件 | 字段 |
|------|------|
| 连接建立 | `clientId`, `roomId`, `remote_addr` |
| 连接关闭 | `clientId`, `roomId`, `reason` |
| 消息推送 | `clientId`, `type`（broadcast/room/unicast）, `msg_size` |
| 心跳超时 | `clientId`, `last_pong` |
| 优雅退出 | `active_connections`, `timeout` |

**示例日志行**：

```json
{"time":"2026-07-05T10:00:00Z","level":"INFO","msg":"连接建立成功","clientId":"user-123","roomId":"room-1","remote_addr":"192.168.1.100"}
```

## 六、测试规范

### 6.1 单元测试

- 使用表驱动测试（Table-Driven Tests）。
- 使用 `net/http/httptest` 测试 HTTP Handler。
- 对于 `service` 层，使用 mock 结构体隔离外部依赖。
- 覆盖率目标：核心模块（`service`）不低于 80%。

### 6.2 集成测试

- 使用 `wscat` 或 Python 脚本模拟 WebSocket 客户端。
- 测试覆盖核心流程：连接建立、消息广播、房间广播、单播、心跳超时、优雅退出。
- 测试用例需包含正常流程和异常流程（如无效参数、超时、连接异常断开等）。

### 6.3 性能测试（压测）

- 使用 `wscat`、`hey` 或自定义 Python 脚本模拟多客户端。
- 压测场景：
  - 连接建立：模拟 1000/5000 个客户端同时连接，测量建立时间。
  - 广播压力：建立 5000 个连接后，通过 HTTP 接口触发广播，观察延迟分布（P50、P99）。
  - 混合负载：广播过程中，部分客户端发送上行消息，验证并发处理能力。

## 七、构建与部署规范

### 7.1 构建命令

```bash
go build -o gateway cmd/gateway/main.go
```

### 7.2 Docker 镜像

- 使用多阶段构建，最终镜像基于 Alpine。
- 镜像大小不超过 50MB。
- 暴露 8080 端口，监听 `0.0.0.0`。

### 7.3 Docker Compose

```yaml
services:
  gateway:
    build: .
    ports:
      - "8080:8080"
    environment:
      - WS_PORT=8080
      - WS_PING_INTERVAL=30
    volumes:
      - ./configs/config.toml:/app/configs/config.toml
    restart: unless-stopped
  redis:  # 可选，多实例扩展时启用
    image: redis:7.2
    ports:
      - "6379:6379"
    profiles:
      - with-redis
```

### 7.4 版本管理

使用 `git tag` 标记版本：

```bash
git tag v1.0.0
git push origin v1.0.0
```

版本号遵循语义化版本规范（Semantic Versioning）：`vMAJOR.MINOR.PATCH`

## 八、版本控制规范

### 8.1 分支策略

| 分支 | 说明 | 合并来源 |
|------|------|----------|
| `main` | 稳定生产版本，受保护分支 | 仅接受来自 `develop` 的 PR |
| `develop` | 开发集成分支 | 所有 `feature/*` 分支 |
| `feature/*` | 功能开发分支，如 `feature/liu-connection-manager` | 从 `develop` 拉出，完成后 PR 回 `develop` |
| `hotfix/*` | 紧急修复分支 | 从 `main` 拉出，完成后 PR 回 `main` 和 `develop` |

### 8.2 提交信息规范

格式：

```
<type>: <subject>

[optional body]
```

**Type 类型**：

| 类型 | 说明 |
|------|------|
| `feat` | 新增功能 |
| `fix` | 修复 Bug |
| `docs` | 文档更新 |
| `refactor` | 代码重构（不改变行为） |
| `test` | 测试相关 |
| `chore` | 构建/工具变动 |

**示例**：

```
feat: 实现 WebSocket 连接升级与注册逻辑
fix: 修复优雅退出时连接未正确关闭的问题
docs: 补充系统设计文档第 4 章数据流设计
```

### 8.3 代码审查清单

提交 PR 前，开发者应确认以下事项：

- [x] 代码符合命名规范（3.1）
- [x] 导出符号有文档注释（3.2）
- [x] 错误处理完备（3.3）
- [x] 无编译警告（`go vet` 通过）
- [x] 核心模块有单元测试（覆盖率 ≥ 80%）
- [x] 日志记录合理（关键事件已记录）
- [x] 配置文件参数已校验
