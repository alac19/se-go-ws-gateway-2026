## 二、评审意见汇总

### 2.1 项目启动阶段评审意见

**会议背景**：项目启动初期，秦勇老师针对选题方向、技术路线和实施步骤给出了指导意见。

**评审意见内容**：

1. **关于项目定位**：老师指出，WebSocket 网关是一个经典的高并发架构项目，本质是对长连接进行管理（如在线聊天场景）。连接管理的核心是 HTTP 服务器对客户端连接的处理和状态维护。

2. **关于技术实现路径**：老师给出了五个实施步骤：
   - 第一步：先安装 WebSocket 组件，调通基础连接
   - 第二步：使用 HTTP 压测工具测试网关性能，关注长连接的稳定性
   - 第三步：找出评价长连接性能的关键指标（如连接数、延迟、吞吐量）
   - 第四步：通过配置优化 WebSocket 内部参数，提升性能
   - 第五步：如果性能仍有瓶颈，再考虑改造长连接的调度机制或模块

3. **关于性能测试要求**：老师指出，最终测试的性能指标没有硬性要求，只需要在自己环境和应用下通过第二步和第三步达到最优即可，重点在于掌握调优的方法论。

4. **关于代码实现**：老师强调 WebSocket 的各个组件已经开源集成好，只需要配置调用即可，但核心业务代码需要自己编写，不能直接复制开源项目的现成实现。

### 2.2 答辩阶段评审意见

**会议背景**：实训答辩当天，项目由罗培友同学进行汇报，秦勇老师听取了项目汇报后给出了点评。

**评审意见内容**：

1. **关于心跳保活机制**：老师指出，当前心跳间隔是固定配置的（通过配置文件和环境变量调整），可以考虑将其改为**动态可调节**的——比如根据连接时长、网络状况等因素自适应调整心跳频率，使系统在不同场景下更加灵活。老师认为这是一个值得深入优化的方向，可以作为后续版本的迭代目标。

2. **关于整体实现**：老师未对其他模块提出质疑或修改意见，项目的核心功能实现得到了认可。

## 三、整改结果

### 3.1 项目启动阶段建议的落实

| 序号 | 评审建议 | 整改措施 | 整改状态 | 说明 |
|------|----------|----------|----------|------|
| 1 | 先安装 WebSocket 组件，调通基础连接 | 安装了 `gorilla/websocket`，实现了 Echo 服务验证 WebSocket 连接 | ✅ 已完成 | 在项目第 1-2 天完成 |
| 2 | 使用 HTTP 压测工具测试网关性能 | 使用 `wscat`、`curl` 和浏览器控制台进行了功能测试和连接验证 | ⚠️ 部分完成 | 因项目周期限制，压测计划延后至后续阶段执行 |
| 3 | 找出评价长连接性能的关键指标 | 在非功能性需求中明确了指标：连接数 ≥ 5,000、P99 延迟 < 50ms、消息吞吐量等 | ✅ 已完成 | 已在需求规格说明书中定义，并通过 Prometheus 指标进行了监控 |
| 4 | 通过配置优化 WebSocket 内部参数 | 实现了完整的配置管理系统（`config.toml` + 环境变量覆盖），支持心跳间隔、读写超时、缓冲区大小等参数的动态调整 | ✅ 已完成 | 所有关键参数均可通过配置文件和环境变量调整 |
| 5 | 改造长连接的调度机制或模块 | 当前架构使用 `connection-per-goroutine` + `channel` 通信模型，已充分利用 Go 的并发优势 | ✅ 已完成 | 核心并发模型已实现，未做底层调度改造，但配置调优已覆盖性能需求 |

### 3.2 答辩阶段建议的落实

| 序号 | 评审建议 | 整改措施 | 整改状态 | 说明 |
|------|----------|----------|----------|------|
| 1 | 心跳间隔可改为动态调节 | 经项目组评估，当前版本继续采用全局配置方案（通过 `config.toml` 和环境变量调整），动态心跳作为后续优化方向 | ⚠️ 暂缓 | 已记录为后续迭代目标；答辩时已向老师说明：全局配置方案已满足当前需求，且可覆盖大多数场景 |

### 3.3 整改总结

通过本次评审，项目组完成了以下整改工作：

1. **需求对齐**：根据评审意见，在需求规格说明书中补充了心跳保活、配置管理等实现细节。
2. **配置管理**：实现了 `config.toml` + 环境变量覆盖的双层配置体系，满足了老师关于“配置调优”的要求。
3. **监控指标**：通过 Prometheus 指标暴露了连接数、消息数等核心性能数据，为后续压测奠定了基础。
4. **动态心跳评估**：对老师提出的动态心跳建议进行了评估，确认当前版本继续使用全局配置方案，并将其纳入后续优化计划。
